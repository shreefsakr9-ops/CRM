# قائمة التحقق الأمني

## قبل الإطلاق (إلزامي)

| # | البند | كيف تتحقق |
| --- | --- | --- |
| 1 | `SEED_DEMO_DATA=false` في الإنتاج | لا توجد حسابات `@bluepoint.local` تجريبية في `/users` |
| 2 | أسرار قوية ومولَّدة عشوائيًا | `SESSION_SECRET` و`FILE_SIGNING_SECRET` بطول 48 بايت من `openssl rand` |
| 3 | لا أسرار داخل Git | `git log -p \| grep -iE "SESSION_SECRET=|PASSWORD=" ` لا يعطي نتائج حقيقية |
| 4 | كلمة مرور المسؤول غُيّرت | أول دخول يفرض التغيير (`mustResetPassword`) |
| 5 | HTTPS يعمل والشهادة صالحة | `curl -I https://<domain>` |
| 6 | PostgreSQL غير مكشوف | `nmap -p 5432 <public-ip>` → مغلق (لا `ports` في compose) |
| 7 | SSH بمفتاح فقط ومقيّد بالـ IP | `PasswordAuthentication no` + قاعدة Ingress ضيقة |
| 8 | Firewall مفعّل | منفذا 80/443 فقط مفتوحان للعامة |
| 9 | النسخ الاحتياطي يعمل | `docker compose logs backup` يظهر نسخة ناجحة |
| 10 | اختبار استعادة تم بنجاح | راجع `docs/06-backup-restore.md` §6 |

## آليات الحماية المطبَّقة في النظام

### المصادقة والجلسات

- كلمات المرور بـ **scrypt** (N=32768, r=8, p=1) مع ملح عشوائي لكل مستخدم — لا تُخزَّن كنص عادي أبدًا.
- سياسة كلمة المرور مفروضة **على السيرفر**: 10 أحرف على الأقل + حرف كبير + صغير + رقم + رفض الكلمات المتوقعة.
- الجلسات مخزَّنة في قاعدة البيانات (وليس JWT) — يمكن إبطالها فورًا.
- الكوكي: `httpOnly` + `SameSite=Lax` + `Secure` في الإنتاج.
- انتهاء صلاحية مزدوج: خمول (4 ساعات افتراضيًا) ومطلق (7 أيام).
- **إبطال تلقائي للجلسات** عند: تعطيل المستخدم، تغيير دوره، تغيير صلاحيات دوره، أو تغيير كلمة المرور.
- تحديد المحاولات: 6 محاولات فاشلة لكل بريد و20 لكل IP خلال 15 دقيقة، مع قفل الحساب 15 دقيقة.
- رسالة خطأ موحّدة للبريد غير الموجود وكلمة المرور الخاطئة (لا نكشف وجود الحساب).
- روابط استعادة كلمة المرور صالحة لساعة واحدة، تُستخدم مرة واحدة، ومخزَّنة كـ hash.

### الصلاحيات

- كل عملية تمر عبر `requirePermission(module, action)` على السيرفر — إخفاء الزر تجميلي فقط.
- نطاق البيانات (`OWN`/`TEAM`/`ALL`) مطبَّق داخل استعلامات Prisma نفسها عبر `scopeWhere()`.
- السجل خارج النطاق يعيد **404 وليس 403** — حتى لا نكشف وجوده.
- الحقول المالية تُحذف من الاستجابة على السيرفر لمن لا يملك `view_financial`، والتكلفة/الربح لمن لا يملك `view_cost_profit`.
- دور `SUPER_ADMIN` غير قابل للتعديل — يمنع فقدان الوصول للنظام.
- **RLS غير مفعّلة** — النطاق مفروض في طبقة الخدمة داخل استعلامات Prisma. السبب والخطة في `docs/02-erd.md` §5.
- سجل التدقيق **للإضافة فقط مفروضًا من قاعدة البيانات**: مشغّلات تمنع UPDATE وDELETE وTRUNCATE حتى على مالك الجداول.

### المدخلات والمخرجات

- كل مدخل يُتحقق منه بـ Zod قبل الوصول لقاعدة البيانات.
- Prisma تستخدم استعلامات مُعامَلية — لا SQL Injection.
- React يهرّب المخرجات افتراضيًا — لا XSS.
- Server Actions محمية من CSRF افتراضيًا في Next.js (فحص Origin).
- رؤوس الأمان: CSP، `X-Frame-Options: DENY`، `nosniff`، `Referrer-Policy`، HSTS في الإنتاج.

### الملفات

- أسماء تخزين عشوائية بالكامل — لا نثق باسم الملف الوارد.
- التحقق من النوع والحجم قبل الحفظ.
- منع الخروج من مجلد التخزين (path traversal) بفحص المسار المطلق.
- روابط موقّعة بـ HMAC صالحة 5 دقائق — **لا وصول عام لأي ملف**.
- التحقق من صلاحية المستخدم على **الكيان المرتبط** وليس على الملف فقط.
- الأنواع غير الآمنة تُحمَّل إجباريًا (`Content-Disposition: attachment`) مع `nosniff`.
- كل تحميل مسجَّل في `file_downloads` و`audit_logs`.
- كل رفع ينشئ إصدارًا جديدًا — لا يُستبدل ملف قديم أبدًا.

### الحوكمة

- `AuditLog` يسجّل: دخول/خروج/محاولات فاشلة، إنشاء/تعديل/حذف/استرجاع، تغيير حالة، تغيير سعر، تغيير صلاحيات، تصدير، وصول للملفات.
- تنقية تلقائية لأي حقل يطابق `password|token|secret|hash|twoFactor` قبل الكتابة في السجل — تحقق منه اختبار في `tests/permissions.test.ts`.
- حذف ناعم افتراضيًا؛ الحذف النهائي يتطلب صلاحية خاصة وتأكيدًا نصيًا.
- الفواتير لا تُحذف — تُلغى مع سبب، حفاظًا على تسلسل الترقيم.

### الإنتاج

- لا تُعرض Stack Traces للمستخدم — `apiError()` تعيد رسالة عامة وتسجّل التفاصيل في سجل السيرفر.
- لا تُسجَّل كلمات مرور أو Tokens في أي سجل.
- الحاوية تعمل بمستخدم غير جذر (`bluepoint`, UID 1001).
- حدود موارد على كل خدمة تمنع استنزاف السيرفر.

## اختبارات أمنية قابلة للتشغيل

```bash
npm test tests/permissions.test.ts
```

تغطي: عزل البيانات بين المستخدمين، نطاق الفريق، حجب الحقول المالية، رفض الوصول غير المصرح به (403)، رفض غير المسجَّل (401)، 404 للسجلات خارج النطاق، الحذف والاسترجاع، وخلو سجل التدقيق من الأسرار.

## المراجعة الدورية

| الدورية | المهمة |
| --- | --- |
| أسبوعيًا | مراجعة `/audit` لعمليات `DELETE` و`PERMISSION_CHANGE` و`EXPORT` |
| شهريًا | مراجعة `/users` وتعطيل حسابات من غادروا الشركة، واختبار استعادة نسخة احتياطية |
| ربع سنويًا | مراجعة مصفوفة الصلاحيات في `/settings/roles`، وتحديث التبعيات (`npm audit`) |
| سنويًا | تدوير `SESSION_SECRET` و`FILE_SIGNING_SECRET` (يتطلب إعادة دخول الجميع) |

## عند الاشتباه في اختراق

1. `docker compose stop app worker` — إيقاف الوصول فورًا.
2. خذ نسخة احتياطية للحالة الراهنة (كدليل).
3. راجع `audit_logs` و`login_attempts` لتحديد النطاق الزمني والحسابات المتأثرة.
4. غيّر `SESSION_SECRET` (يُبطل كل الجلسات) وكل كلمات المرور.
5. راجع سجلات Caddy: `docker compose exec caddy cat /data/access.log`.
6. أعد التشغيل بعد التأكد، وأبلغ الإدارة.

## المصادقة الثنائية (TOTP)

| البند | التطبيق |
| --- | --- |
| الخوارزمية | TOTP وفق RFC 6238 مبنية على `node:crypto` — بلا تبعية خارجية تتعامل مع أسرار المصادقة. مُتحقَّق منها بمتجهات الاختبار المنشورة في الـRFC. |
| السر | ١٦٠ بت عشوائية، لا يُفعَّل إلا بعد إثبات المستخدم أنه قرأه (رمز صحيح)، ولا يُعاد عرضه بعد التفعيل. |
| رمز QR | يُولَّد على السيرفر ويُضمَّن كـSVG — السر لا يخرج إلى أي خدمة خارجية. |
| إعادة الاستخدام | كل رمز يُقبل مرة واحدة: تُخزَّن آخر خطوة زمنية مقبولة ويُرفض ما يساويها أو يسبقها. |
| رموز الاسترجاع | عشرة رموز تُعرض مرة واحدة وتُخزَّن مجزّأة (SHA-256)، كل رمز يُستهلك مرة واحدة. |
| تغيير الإعدادات | الإيقاف وإعادة التوليد يتطلبان كلمة المرور الحالية — سرقة الجلسة وحدها لا تكفي. |
| فقد الجهاز | إعادة تعيين إدارية صريحة تُنهي كل جلسات المستخدم، وتُسجَّل في سجل التدقيق، ويصل إشعار أمني لصاحب الحساب. |
| قبل التحقق | لا تُنشأ أي جلسة قبل نجاح العامل الثاني. كوكي التحدي موقّع بـHMAC، عمره خمس دقائق، ولا يمنح أي وصول بذاته. |
| الإلزام حسب الدور | أدوار محددة في الإعدادات لا تصل إلى أي بيانات قبل التفعيل — يُفرض في حارس تخطيط التطبيق، وصفحة التفعيل خارج المجموعة حتى لا تدور إعادة التوجيه. |
| حد المعدل | محاولات العامل الثاني الفاشلة تُحسب ضمن نفس حد محاولات الدخول. |

### حذف الأسرار افتراضيًا من طبقة البيانات

`include` في Prisma يعيد **كل** أعمدة الجدول، ونتائج الاستعلامات تُمرَّر إلى مكوّنات
العميل فتُسلسَل داخل صفحة HTML. الاعتماد على تذكّر كتابة `select` في كل مرة فشل فعلًا:
كان hash كلمة مرور كل مستخدم يظهر في صفحة `/users`.

الحل البنيوي في `src/server/db.ts`: عميل Prisma مضبوط على حذف الأسرار من **كل**
استعلام، بما في ذلك العلاقات المتداخلة:

| الجدول | الحقول المحذوفة |
| --- | --- |
| `users` | `passwordHash`, `twoFactorSecret` |
| `sessions` | `tokenHash` |
| `password_reset_tokens` | `tokenHash` |
| `two_factor_recovery_codes` | `codeHash` |

من يحتاجها فعلًا — طبقة المصادقة وحدها — يطلبها صراحةً:

```ts
prisma.user.findUnique({ where: { email }, omit: { passwordHash: false } })
```

فيصير الوصول إلى السر قرارًا ظاهرًا في الكود بدل سلوك افتراضي صامت. الكتابة
والتصفية بـ`where` لا تتأثران. تغطي `tests/permissions.test.ts` هذا السلوك.

> **تحقّق دوري مقترح**: تصفّح كل صفحات النظام كمسؤول وابحث في مصدر الصفحة عن
> `passwordHash` و`scrypt$` و`twoFactorSecret`. هكذا اكتُشف التسريب أول مرة.
